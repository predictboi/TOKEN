# 프로젝트 소개서: 시장이 가격을 매기는 Solana 프로젝트 신용등급

작성일: 2026-09-09
상태: 해커톤 MVP 스펙 v1 (개선안 반영)

---

## 0. 한 문장

**Solana 프로젝트에 대한 월간 "부도 보험 시장"을 열고, 그 보험료율의 누적 이력을 온체인 신용등급으로 기록하는 프로토콜.**

무디스가 애널리스트로 등급을 매긴다면, 여기서는 자기 돈을 건 시장이 등급을 매깁니다. 프로젝트는 돈을 내고 등급을 사는 것이 아니라, 자기 등급에 자기 돈을 겁니다.

---

## 1. 참여자 5종과 각자가 얻는 것

| 참여자 | 하는 일 | 얻는 것 |
|---|---|---|
| **프로젝트 (Issuer)** | 등록, 월간 온체인 요건 선언, 셀프 스테이크 예치 | 온체인 신용등급, 투자자·런치패드·렌딩에 제시할 검증 가능한 이력 |
| **인수자 (Pass 측, Underwriter)** | USDC를 인수 풀에 예치 | 운용 수익 + 보험료 배분. 부도 시 예치금 일부 손실 |
| **보호 구매자 (Default 측, Protection buyer)** | 보험료를 내고 커버리지 구매 | 부도 시 커버리지 금액 전액 수령. 손실 상한 = 낸 보험료 |
| **크랭커 (Resolver)** | 에포크 종료 후 정산 인스트럭션 호출 | 소액 정산 보상 (permissionless) |
| **등급 소비자** | 런치패드, 렌딩, 지갑, 트레이더가 등급 계정을 읽음 | 프로젝트 리스크를 숫자 하나로 확인 |

핵심 규칙: **프로젝트는 자기 시장의 Pass 측에만 참여할 수 있고(의무 셀프 스테이크), Default 측은 살 수 없습니다.** 내부자가 자기 부도에 베팅하는 길을 막습니다.

## 2. 에포크 한 바퀴 (30일)

```
D-0   프로젝트 등록: 요건 3종 선언 + 셀프 스테이크 예치 (예: 20,000 USDC)
D-0   에포크 오픈: 요건 기준값 스냅샷 (트레저리 잔고, 업그레이드 권한, 팀 지갑 잔고)
D-0~  인수자: Pass 풀에 USDC 예치 → 풀 자본은 수익 vault에 예치
D-0~  보호 구매자: 커버리지 구매, 보험료 = 커버리지 × 그 시점 보험료율
      보험료율은 이용률(팔린 커버리지 / 풀 자본)에 따라 곡선으로 올라감
D-30  누구나 resolve 호출 → 프로그램이 요건 3종을 온체인에서 직접 검증
      PASS: 보험료 + 운용 수익을 인수자에게 분배, 셀프 스테이크 반환
      DEFAULT: 커버리지를 보호 구매자에게 지급, 셀프 스테이크 슬래시
D-30  등급 계정 갱신: 연속 Pass 횟수, 마감 보험료율, 셀프 스테이크 비율
```

### 보험료율 곡선 (시장이 가격을 정하는 부분)

```
월 보험료율 r(u) = r_min + (r_max − r_min) × u²
u = 팔린 커버리지 / Pass 풀 자본  (0 ≤ u ≤ 1)
기본값: r_min = 0.5%/월, r_max = 15%/월
```

보호 수요가 몰리면 u가 오르고 r이 오릅니다. 이 r이 곧 **시장이 매긴 월간 부도 확률**입니다. 오더북 없이도 가격 발견이 일어나고, 프로그램 안에서 계산되므로 오라클이 필요 없습니다.

### 요건 3종 (v1, 전부 프로그램 안에서 직접 검증)

| 요건 | 검증 방법 | 계정 |
|---|---|---|
| 업그레이드 권한 불변 | 등록 시 기록한 authority와 현재 ProgramData의 authority 비교 | 프로젝트 프로그램의 ProgramData |
| 트레저리 잔고 유지 | 등록 시 선언한 최소 잔고 ≥ 현재 토큰 계정 잔고 | 트레저리 토큰 계정 |
| 팀 지갑 무매도 | 에포크 오픈 시 스냅샷 잔고 − 현재 잔고 ≤ 허용 감소량 | 팀 토큰 계정 (복수 가능) |

세 가지 모두 `resolve` 인스트럭션에 해당 계정을 넘기면 프로그램이 읽어서 판정합니다. 외부 오라클, 인덱서, 투표가 필요 없습니다. 이것이 "누가 진실을 정하는가"에 대한 답입니다.

## 3. 수익 구조

### 3.1 수익원 4가지

| # | 수익원 | 요율 (초기값) | 발생 시점 | 성격 |
|---|---|---|---|---|
| 1 | **보험료 수수료** | 보호 구매자가 낸 보험료의 10% | 커버리지 구매 시 즉시 | 거래량 비례 |
| 2 | **운용 수익 수수료** | Pass 풀 운용 수익의 20% | 에포크 정산 시 | TVL 비례 |
| 3 | **슬래시 수수료** | 부도 시 슬래시된 셀프 스테이크의 10% | 부도 정산 시 | 이벤트성 |
| 4 | **등급 API 구독** | 월정액 (런치패드·렌딩·지갑 대상) | v2 | B2B, 가장 큰 장기 수익 |

등록 수수료는 **받지 않습니다.** 콜드 스타트 때문이기도 하고, "돈 내고 등급 산다"는 인상을 피하기 위해서이기도 합니다. 프로젝트가 내는 것은 수수료가 아니라 **위험 부담(셀프 스테이크)** 입니다.

### 3.2 프로젝트 1개, 에포크 1회 숫자 예시

가정: Pass 풀 자본 200,000 USDC, 팔린 커버리지 60,000 USDC (u = 0.3), 셀프 스테이크 20,000 USDC, 운용 수익 연 5%.

| 항목 | 계산 | 금액 |
|---|---|---|
| 보험료율 | 0.5% + 14.5% × 0.09 | 1.81%/월 |
| 보험료 총액 | 60,000 × 1.81% | 1,086 USDC |
| 운용 수익 | 200,000 × 5% ÷ 12 | 833 USDC |

**PASS로 끝난 경우**

| 수취자 | 금액 |
|---|---|
| 프로토콜 (보험료 10%) | 109 |
| 프로토콜 (운용 수익 20%) | 167 |
| 인수자 (나머지 보험료 + 운용 수익) | 977 + 666 = 1,643 → 풀 대비 월 0.82%, 연환산 약 9.9% |
| 프로젝트 | 셀프 스테이크 20,000 반환 |
| 보호 구매자 | 보험료 1,086 소멸 |
| **프로토콜 합계** | **276 USDC** |

**DEFAULT로 끝난 경우**

| 수취자 | 금액 |
|---|---|
| 보호 구매자 | 커버리지 60,000 (Pass 풀에서) + 슬래시 18,000 = 78,000. 투입 1,086 대비 약 72배 |
| 인수자 | 200,000 − 60,000 + 977 + 666 = 141,643 (약 −29%) |
| 프로토콜 (보험료 10%) | 109 |
| 프로토콜 (운용 수익 20%) | 167 |
| 프로토콜 (슬래시 10%) | 2,000 |
| **프로토콜 합계** | **2,276 USDC** |

### 3.3 규모별 월 수익 추정 (수익원 1~3만)

| 등록 프로젝트 | 평균 풀 자본 | 월 프로토콜 수익 (부도율 3% 가정) |
|---|---|---|
| 10 | 100k | 약 1.7k USDC |
| 100 | 150k | 약 25k USDC |
| 500 | 200k | 약 170k USDC |

솔직한 평가: 수익원 1~3만으로는 해커톤 이후 초기 1년은 작은 사업입니다. **진짜 사업은 수익원 4**입니다. 등급이 런치패드 게이팅, 렌딩 담보 파라미터, 지갑 경고 UI에 들어가는 순간 B2B 구독이 됩니다. 시장(1~3)은 등급의 신뢰를 만드는 장치이고, 등급(4)이 상품입니다. 피치에서는 이 순서로 말합니다.

### 3.4 왜 각 참여자가 들어오는가

- **인수자**: USDC로 연 8~12% (운용 수익 5% + 보험료). 리스크는 Kamino 예치보다 높고 밈코인 LP보다 낮은 중간 구간. 이 구간은 Solana에 상품이 거의 없습니다.
- **보호 구매자**: 토큰 보유자와 LP의 헤지 수요. 에어드랍 파머의 헤지 수요. 순수 투기 수요(수십 배 페이아웃). 세 가지가 섞여야 유동성이 생깁니다.
- **프로젝트**: 초기에는 무료로 "우리는 자기 돈을 걸었다"는 신호를 삽니다. 런치패드와 렌딩이 등급을 요구하기 시작하면 선택이 아니라 필수가 됩니다.

## 4. 무엇을 개발해야 하는가

### 4.1 전체 구조

```
┌──────────────────────────────────────────────────────────┐
│  프론트엔드 (Next.js)                                       │
│  프로젝트 목록 · 프로젝트 상세 · Pass 예치 · Default 구매 · 등록 │
└───────────────┬───────────────────────────┬──────────────┘
                │ RPC / 지갑                  │ REST
┌───────────────▼──────────────┐  ┌──────────▼──────────────┐
│  온체인 프로그램 (Anchor/Rust)   │  │  인덱서 + 등급 API (TS)    │
│  Project · Epoch · Position    │  │  체인 읽기 → 등급 계산 → JSON │
│  register · open · deposit ·   │  │  (수익원 4의 원형)           │
│  buy_coverage · resolve · claim│  └─────────────────────────┘
└───────────────┬──────────────┘
                │ CPI
┌───────────────▼──────────────┐
│  수익 Vault 어댑터              │
│  v1: 프로토콜 자체 mock vault   │
│  v2: Kamino USDC / Meteora DAMM v2 스테이블 풀 │
└──────────────────────────────┘
```

### 4.2 온체인 프로그램 (핵심, 개발 비중 50%)

**계정 (PDA)**

| 계정 | 키 | 주요 필드 |
|---|---|---|
| `Protocol` | 싱글턴 | admin, fee 요율 3종, r_min, r_max, 에포크 길이, 수수료 트레저리 |
| `Project` | project_id | owner, 요건 3종 파라미터(program_id·authority, 트레저리 계정·최소잔고, 팀 계정 목록·허용 감소량), 셀프 스테이크 금액, **등급 필드**(consecutive_pass, total_epochs, last_rate_bps, defaults) |
| `Epoch` | project + index | 시작·종료 slot, 스냅샷 값들, pool_capital, coverage_sold, premium_collected, yield_accrued, 상태(Open/Passed/Defaulted), 정산 비율 |
| `UnderwriterPosition` | epoch + wallet | 예치 금액, claim 여부 |
| `CoveragePosition` | epoch + wallet | 커버리지 금액, 낸 보험료, claim 여부 |

`Project` 계정 자체가 **온체인 등급 어테스테이션**입니다. 다른 프로그램이 이 PDA를 읽으면 됩니다.

**인스트럭션**

| 순서 | 인스트럭션 | 호출자 | 하는 일 |
|---|---|---|---|
| 1 | `initialize_protocol` | admin | 요율·곡선 파라미터 설정 |
| 2 | `register_project` | 프로젝트 | 요건 3종 등록, 셀프 스테이크 USDC 예치 |
| 3 | `open_epoch` | 누구나 | 스냅샷 기록(권한, 잔고들), Epoch 계정 생성 |
| 4 | `deposit_underwriting` | 인수자 | Pass 풀에 USDC 예치, vault로 CPI |
| 5 | `buy_coverage` | 보호 구매자 | 현재 u로 r 계산, 보험료 징수(10% 수수료 분리), 커버리지 기록. u ≤ 1 강제 |
| 6 | `resolve_epoch` | 누구나 (종료 후) | 요건 3종 검증 → Passed/Defaulted 확정, 슬래시·분배 비율 계산 |
| 7 | `claim` | 인수자·구매자 | 포지션별 정산금 수령 |
| 8 | `withdraw_self_stake` | 프로젝트 | Pass 후 셀프 스테이크 회수 (또는 다음 에포크 롤오버) |

해커톤 데모에 반드시 필요한 것은 2, 3, 4, 5, 6, 7입니다. 1은 배포 스크립트, 8은 있으면 좋습니다.

**설계상 결정 사항**

- 에포크 길이는 slot 기반 파라미터로 두고, 데모에서는 10분짜리 에포크로 한 바퀴를 보여줍니다.
- `buy_coverage`의 r은 구매 직전 u로 계산합니다(단순화). 대량 구매가 가격을 뛰어넘는 문제는 v2에서 구간 적분으로 해결합니다.
- 부도 시 인수자 손실은 pro-rata입니다. 트랜치(선순위/후순위)는 v2. Senthos 같은 팀이 이 위에 트랜치를 얹는 그림이 됩니다.
- 요건 검증 실패 시 판정을 뒤집을 이의제기 절차는 v1에 없습니다. 판정이 전부 온체인 결정적이라 필요성이 낮습니다.

### 4.3 수익 Vault 어댑터 (개발 비중 10%)

- v1: 프로그램 내부 "mock vault". 예치금을 보관하고 정산 시 관리자가 넣어둔 시뮬레이션 수익률을 적용. 데모에서 수익 흐름을 보여주기 위한 용도.
- v2: Kamino USDC 마켓 예치 CPI. Meteora DAMM v2 스테이블 풀은 그 다음. **변동성 풀은 넣지 않습니다.** 인수자 원금이 비영구 손실로 깎이면 "Pass 측은 원금 보전"이라는 약속이 깨집니다.

### 4.4 인덱서 + 등급 API (개발 비중 15%)

- Helius RPC로 `Project`·`Epoch` 계정을 읽어 DB에 적재.
- 등급 산식 (v1):

```
score = 40 × min(consecutive_pass, 12)/12
      + 40 × (1 − 최근 6 에포크 평균 r / r_max)
      + 20 × min(self_stake / avg_pool_capital, 0.2)/0.2
등급: ≥85 AAA, ≥75 AA, ≥65 A, ≥55 BBB, ≥45 BB, ≥35 B, ≥20 CCC, 부도 이력 있으면 한 단계 강등, 미정산 부도 D
```

- 엔드포인트: `GET /projects`, `GET /projects/:id` (등급, 이력, 현재 r), `GET /projects/:id/badge.svg` (임베드용). 이것이 수익원 4의 원형입니다.

### 4.5 프론트엔드 (개발 비중 25%)

화면 5개. 더 만들지 않습니다.

1. **프로젝트 목록**: 등급, 현재 보험료율, 풀 자본, 이용률, 연속 Pass 횟수. 등급별 정렬.
2. **프로젝트 상세**: 요건 3종과 현재 값(실시간), 에포크 타임라인, 보험료율 곡선 위 현재 위치, 등급 이력.
3. **인수 (Pass)**: 금액 입력 → 예상 수익률(운용 + 보험료) 표시 → 예치.
4. **보호 구매 (Default)**: 커버리지 입력 → 보험료와 부도 시 수령액 표시 → 구매.
5. **프로젝트 등록**: 프로그램 ID, 트레저리 계정, 팀 계정, 최소 잔고, 셀프 스테이크 입력.

### 4.6 데모 데이터

devnet에 실제 Solana 프로젝트 3~5개를 흉내낸 더미(프로그램 + 트레저리 + 팀 지갑)를 배포하고, 그중 하나는 데모 중 트레저리를 빼내 **Default가 실제로 판정되는 장면**을 보여줍니다. 심사위원이 60초 안에 이해하는 장면은 이것입니다.

### 4.7 기술 스택

- Anchor 0.31+, Solana CLI v3, Rust
- create-solana-dapp `nextjs-anchor` 템플릿, TypeScript, Helius RPC
- 인덱서: Node + SQLite(데모) 또는 Postgres

## 6. 아직 정하지 않은 것 (팀 결정 필요)

1. 셀프 스테이크 최소 비율: 풀 자본 대비 고정 비율인지, 절대 금액인지.
2. 부도 시 인수자 손실 상한을 둘지(예: 풀의 50%). 두면 커버리지 판매 상한도 같이 내려감.
3. 에포크 사이 인수 자본 자동 롤오버 여부. 있으면 UX가 좋지만 리스크 고지가 복잡해짐.
4. 등급 산식을 온체인에 둘지(다른 프로그램이 직접 읽기 좋음) 오프체인에 둘지(바꾸기 쉬움). v1은 오프체인 권장, 원천 데이터만 온체인.
5. 미국 유저 지오블록 범위.
